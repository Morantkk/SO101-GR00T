# 02 · 数据采集

采集质量决定上限。这个项目走过最贵的弯路，都不是训练参数问题，而是采集与预处理。

---

## 一、先想清楚任务粒度

| 任务 | 集数 | 每集时长 | 结果 |
|---|---|---|---|
| 抓单支笔放进盒子（v1） | 50 | 20~30 s | ✅ 能稳定完成 |
| 抓走桌上 3~5 个物体全部放进盒子（v3） | 102 | 30~50 s | ❌ 真机抓空（数据错位，见 03） |

经验：

- **单个物体的任务，50 集就够**（17,789 帧，batch 16 下约 9 epoch 收敛）。
- **长任务每集塞的动作越多，单步监督信号越稀**。v3 一集里有 3~5 次抓取，
  模型要同时学会"找物体、绕开已抓走的、判断剩余"，失败面成倍增加。
  建议先做单物体，把管道跑通再说多物体。
- 一条演示最好**只包含一个完整动作周期**（官方文档原话："每条 episode 必须是一个完整动作周期，且 idle 帧已去掉"）。

## 二、采集参数（与训练严格一致）

```bash
lerobot-record \
  --robot.type=so101_follower \
  --robot.port=COM3 \
  --robot.id=my_awesome_follower_arm \
  --robot.cameras="{ front: {type: opencv, index_or_path: 1, width: 640, height: 360, fps: 15}, wrist: {type: opencv, index_or_path: 0, width: 1280, height: 720, fps: 15} }" \
  --teleop.type=so101_leader \
  --teleop.port=COM4 \
  --teleop.id=my_awesome_leader_arm \
  --dataset.repo_id=local/arm101_pick_one_pen \
  --dataset.root="E:/lerobot_datasets/arm101_pick_one_pen" \
  --dataset.single_task="Pick up a pen and put it into the box" \
  --dataset.fps=15 \
  --dataset.episode_time_s=40 \
  --dataset.reset_time_s=8 \
  --dataset.num_episodes=50 \
  --dataset.push_to_hub=false \
  --dataset.rgb_encoder.vcodec=h264 \
  --dataset.rgb_encoder.crf=18 \
  --display_data=true
```

逐项说明：

| 参数 | 值 | 为什么 |
|---|---|---|
| `--dataset.fps` | **15** | 默认 30。改成 15 后既省带宽也让 16 步的 chunk 覆盖 ~1 s，与训练/推理统一 |
| `front` 相机 | index 1, 640×360 | 原生支持；训练也吃这个尺寸，不用二次缩放 |
| `wrist` 相机 | index 0, 1280×720 | 这台设备不支持 640×360，只能录 720p，训练前用 `92` 缩到 360p |
| `episode_time_s` | 40 | 抓笔实际用 20~30 s，留余量；**宁可长一点也别不够**（超时会被截断） |
| `reset_time_s` | 8 | 复位时间**不计入数据**，够你摆好下一个物体 |
| `push_to_hub` | **false** | 默认 true，会给一个没登录 HF 的机器报错 |
| `vcodec` | **h264** | lerobot 默认 `libsvtav1`。AV1 在部分解码链上会出问题，训练集也统一用 h264 |

> ⚠️ **`--dataset.single_task` 必须和数据集里最终的 task 字符串一字不差**。
> GR00T 是语言条件策略，推理时传的文本和训练时的文本不一致，会直接影响行为。
> 本项目 v1 用的就是 `Pick up a pen and put it into the box`。

## 三、采集习惯（比参数重要得多）

### 1. 每集从同一个 home 位姿开始

v1 的 102 集（v3）里，起始位姿 `shoulder_lift` 的标准差只有 **3.77°** —— 这是数据里最宝贵的性质。
一旦每条演示从不同位姿起跑，"同一个指令"就对应几百种起始状态，模型只能学出一个"平均起步"。

后来有一次为了绕开关节极限，把数据多裁了 10 帧，结果起始 std 从 3.77° 涨到 **13.50°**（放大 3.5 倍），
直接废掉这个优点。**要改起始位姿就改客户端，不要改数据。**

### 2. 按下开始键那一刻手就该在动

旧数据里每集开头残留 46~124 帧（3~8 秒）静止段，主要靠后处理裁。
但后处理裁剪如果不重写 `timestamp`，就会踩那个致命 bug（见 03）。

更省事的做法：**录制时不要停在开头**。`reset_time_s` 里把臂摆好，按下后立刻开始动作。

### 3. 每条演示结尾也停稳

结尾停在 home 附近，不要停在半空。否则下一次 `reset` 要从半空拉回来，容易撞到东西。

### 4. 物体位置要随机

固定位置会让模型学会"记住桌面绝对坐标"而不是"看图找物体"。
v1 采集时每次都把笔放在桌面上**不同的位置和朝向**，这是它能泛化到新位置的原因；
如果 50 集全摆同一个点，模型学到的就是一张坐标表，换个位置就失效。

### 5. 失败也要录

v1/v3 的 439 次合爪里 **0 次重试** —— 演示里从来没有"抓空了再抓一次"。
结果就是模型完全没有失败恢复能力，一旦抓空就永久卡住。

> 采集时如果抓歪了，**别按重录**，把"发现没抓到 → 退回来 → 重新对准 → 抓住"整段录进去。
> 这类样本比 10 条成功演示更值钱。

### 6. 每 10 集抽查一次

```bash
lerobot-dataset-viz --repo-id local/arm101_pick_one_pen --root E:/lerobot_datasets/arm101_pick_one_pen
```

看两件事：**画面里物体清不清楚**、**关节曲线是否连续**（有没有跳变）。
60 集录完再返工的代价远大于每 10 集看一眼。

## 四、相机怎么摆（决定任务上限）

GR00T 会把输入**各向异性**缩到 224×224。以 640×360 为例：x 方向 ×0.35、y 方向 ×0.62，
patch 14 ⇒ 每路 16×16 = 256 个 token，**一个 token 覆盖原图约 38×21 像素**。

这意味着：

| 物体宽度 | 在画面里占几个 token | 效果 |
|---|---|---|
| 25 px（马克笔） | ≈ 1 | 只知道"那里有东西"，不知道偏左还是偏右 2 mm |
| 150 px（大杯子） | ≈ 4 | 位置可辨，能对准 |

**v3 的实测现象正好对上**：合爪半径系统性偏外 5~8 cm（演示 0.229 m vs 运行 0.276~0.305 m），
闭环下合爪方位的标准差只有演示的 46% —— 位置信息被平均掉了。
（观测于 102 集的全物体任务；单物体的 v1 没有做这项统计。）

所以：

- **相机往工作区推**，让目标物体占画面中央 1/3 以上；
- 腕部相机压低，让夹爪与目标同框（腕部视角对"精确落点"贡献更大）；
- 录 2~3 集后做一次"看得清吗"检查：把 640×360 缩到 224，肉眼看目标还在不在。

检查相机是否被人碰过（跨天复用同一套标定）：

```bash
python scripts/diagnose/127b_view_matrix.py --ds <数据集> --episodes 0,1,2
```

它用相位相关估计不同 episode 之间的画面位移。实测两次真机摆放相差 0 位移，
仅 x 方向稳定偏 ~9 px（≈0.8 cm），量级不足以解释抓空 —— 也就是说**相机没被挪**。

## 五、采样预算

| 项目 | v1 | v3 |
|---|---|---|
| 集数 | 50 | 102 |
| 总帧数 | 17,789 | 51,209 |
| 单集帧数 | 中位 356 | 中位 486 |
| 磁盘占用 | 375 MB | 1.4 GB |
| 录制耗时 | ~40 min | ~2.5 h |
| 训练步数 | 10,000 | 30,000 |

经验公式：`batch 16` 下 1 epoch ≈ 总帧数 / 16 步。v1 ≈ 1,112 步/epoch，
跑 10,000 步 = 9 epoch，刚好收敛且不过拟合。
